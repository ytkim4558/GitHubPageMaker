AI 코딩 보조 도구가 발달하면서 우리는 단순한 질의응답(Ask)을 넘어, 내 PC에서 직접 코드를 수정하고 터미널을 제어하는 자율형 에이전트(Agent)를 사용하기 시작했다. 하지만 도구 제공자가 만들어둔 기본 CLI 환경을 그대로 사용하다 보면, 개발 흐름을 끊어먹는 치명적인 병목들을 마주하게 된다.

이번 글에서는 이 병목들을 완전히 제거하고, 나만의 **AI-Native 개발 워크플로우**를 구축하기 위해 적용한 세 가지 시스템 레벨의 최적화 도입기를 공유한다.

---

## 1. YOLO (자동 승인) 모드 구축: 인간의 개입을 없애다

가장 먼저 겪는 불편함은 권한 승인이다. 에이전트가 파일 하나를 고치거나 터미널 명령어를 실행할 때마다 `(Y/N)`을 묻는 팝업이나 프롬프트가 뜬다. 안전을 위한 조치라지만, 개발자가 수십 번씩 엔터를 쳐야 한다면 그것은 더 이상 '자동화'가 아니다.

이 문제를 해결하기 위해 시스템 설정 파일의 권한 화이트리스트에 와일드카드(`*`)를 강제 주입하여, 이른바 **YOLO(You Only Look Once) 모드**를 구축했다. 
안전이라는 핑계로 발생하는 문맥 스위칭(Context Switching)을 과감히 포기한 대신, 에이전트에게 목적만 던져두고 나는 다른 작업을 할 수 있는 진정한 의미의 '비동기 개발 환경'을 얻었다.

## 2. TUI 기반 Resume 브라우저 개발: 작업 기억의 시각화

두 번째 문제는 '문맥 단절'이다. CLI 창을 무심코 닫거나 재부팅을 하면, 에이전트는 지금까지 내가 설명했던 프로젝트의 방향성이나 작업 상태를 모두 잊어버린다. 세션 ID를 찾아 복구(`resume`)할 수는 있지만, 수많은 16진수 ID 텍스트 더미 속에서 "그때 그 작업"을 찾아내기란 불가능에 가깝다.

그래서 단순히 명령어를 입력하는 방식을 버리고, 과거 세션 로그 폴더를 직접 스캔하여 터미널 내부에 시각적인 두 패널 UI를 띄우는 **TUI(Text User Interface) 기반 Resume 브라우저**를 별도로 개발해 연동했다.

방향키로 과거 작업 목록을 훑어보면 AI가 요약한 당시의 작업 내용이 프리뷰로 뜬다. 그리고 엔터 한 번이면 에이전트는 과거의 기억(Context)을 그대로 가지고 부활한다. 세션 복구 도구의 본질은 ID를 치는 것이 아니라, **'작업 기억을 시각적으로 다시 찾게 해주는 브라우저'**라는 철학을 구현한 것이다.

## 3. 터미널 렌더링 최적화: 사소한 버그가 만드는 거대한 오해

마지막은 터미널 텍스트 렌더링 버그다. 에이전트가 한글과 영문 코드를 섞어 출력할 때, Windows 터미널의 폰트 폭 계산 문제나 인코딩 충돌로 특정 글자가 증발하는 현상이 발생하곤 한다. 이럴 경우 개발자는 "AI가 코드를 잘못 짰다"고 오해하기 쉽다.

이를 원천 차단하기 위해 PowerShell 프로필에 I/O 인코딩을 UTF-8로 강제하고, 터미널 기본 폰트를 한글 폭 계산에 최적화된 `D2Coding`과 `Cascadia Mono`의 폴백 조합으로 강제 덮어씌웠다. 아주 사소한 환경 세팅 같지만, 이것이 뒷받침되지 않으면 AI가 뱉어내는 코드를 100% 신뢰할 수 없게 된다.

---

## 결론: AI-Native의 완성은 시스템 튜닝에서 시작된다

이처럼 극단적으로 최적화된 워크플로우를 세팅하는 사람은 많지 않다. 대부분은 제공되는 도구에 순응하며 불편함을 감수한다. 

하지만 AI를 단순한 보조 도구가 아니라 **"손발을 직접 움직이는 완벽한 팀원"**으로 대우하려면, 그 팀원이 가장 빠르고 정확하게 달릴 수 있도록 운영체제(OS) 수준에서부터 트랙을 깔아줘야 한다. AI-Native 개발은 단순히 좋은 프롬프트를 쓰는 것이 아니라, 자신의 작업 방식에 맞춰 환경을 깎아내는 것에서부터 완성된다.
